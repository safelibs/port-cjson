1. **High-level architecture.**

`safe/Cargo.toml` is a two-member workspace at version `1.7.17`, with `crates/libcjson` and `crates/libcjson_utils` as the only members. `safe/crates/libcjson/Cargo.toml` builds the core crate as `safe-libcjson`, and `safe/crates/libcjson_utils/Cargo.toml` builds the utils crate as `safe-libcjson-utils`; both crates emit `cdylib` and `staticlib` artifacts and both use checked-in `build.rs` files.

The build is a Cargo/CMake bridge, not a code generator. `safe/crates/libcjson/build.rs` watches `CJSON_ENABLE_LOCALES` and `CJSON_SONAME`, enables the `cjson_enable_locales` cfg when requested, and injects the core SONAME. `safe/crates/libcjson_utils/build.rs` watches `CJSON_CORE_LIBRARY_DIR` and `CJSON_UTILS_SONAME`, adds the core library search path, links the utils crate against `cjson`, and injects the utils SONAME. `safe/CMakeLists.txt:252-299` is the bridge point: it runs `cargo build` for `safe-libcjson` and `safe-libcjson-utils`, passes the exact environment variables `CJSON_ENABLE_LOCALES`, `CJSON_SONAME`, `CJSON_CORE_LIBRARY_DIR`, and `CJSON_UTILS_SONAME`, and declares both `build.rs` files as explicit dependencies. Earlier CMake logic (`safe/CMakeLists.txt:167-240`) wraps the Rust static archives into shared libraries with `safe/abi/libcjson.map` and `safe/abi/libcjson_utils.map`, assigns SONAME symlinks, and links through the C toolchain. Later install logic (`safe/CMakeLists.txt:483-557`) installs the libraries, pkg-config files, and CMake package exports, and `safe/CMakeLists.txt:565-569` enables the C test subtree.

The header surface is checked in. `safe/include/cjson/cJSON.h` and `safe/include/cjson/cJSON_Utils.h` are the canonical public headers. `safe/cJSON.h` and `safe/cJSON_Utils.h` are source-tree wrapper headers that include those canonical files. The install contract is driven by CMake and pkg-config, not by installing the root-level wrappers: `safe/CMakeLists.txt:353-358`, `safe/library_config/cJSONConfig.cmake.in:7-10`, `safe/library_config/libcjson.pc.in:1-11`, and `safe/library_config/libcjson_utils.pc.in:1-11` all expose both `include/` and `include/cjson/`, which is why installed `#include <cJSON.h>` and `#include <cJSON_Utils.h>` work. `safe/debian/libcjson-dev.install:1-2` installs the canonical `cJSON.h` and `cJSON_Utils.h` headers under the package include directory; it does not install the root wrappers. There is no `cbindgen` or `bindgen` pipeline anywhere under `safe/` or `.github/`; the build uses the checked-in headers, `build.rs`, and CMake as the source of truth.

Within the core crate, `safe/crates/libcjson/src/lib.rs` is the entry point that splits the implementation into `abi`, `hooks`, `parse`, `print`, `string`, `number`, `list`, `mutate`, `create`, `delete`, `duplicate`, `compare`, `minify`, `tree`, `typecheck`, and `error`. `safe/crates/libcjson/src/abi.rs` fixes the `cJSON` layout and hook types at the C ABI boundary. `parse.rs`, `string.rs`, and `number.rs` turn caller-supplied byte buffers into `cJSON` trees; `print.rs` renders trees back to text; `list.rs`, `mutate.rs`, and `tree.rs` maintain the intrusive linked-list structure that cJSON exposes; `create.rs`, `delete.rs`, `duplicate.rs`, `compare.rs`, `typecheck.rs`, `minify.rs`, and `error.rs` implement the rest of the exported core API surface; and `hooks.rs` owns allocator-hook indirection.

`safe/crates/libcjson_utils/src/lib.rs` is the entry point for the utils library. It locally redefines the public `cJSON` layout, declares `extern "C"` imports for core entrypoints such as `cJSON_CreateArray`, `cJSON_GetObjectItemCaseSensitive`, `cJSON_Duplicate`, `cJSON_malloc`, and `cJSON_free`, and then implements JSON Pointer, JSON Patch, Merge Patch, and object sorting in `pointer.rs`, `patch.rs`, `merge_patch.rs`, and `sort.rs`. That makes the utils crate internally coupled to the core shared library through the exported C ABI, even though both are Rust code in the same workspace.

Packaging and CI stay tied to the checked-in safe tree. `safe/debian/control`, `safe/debian/rules`, `safe/debian/libcjson-dev.install`, `safe/debian/libcjson1.install`, and `safe/debian/libcjson1.symbols` define the Debian packaging contract; `safe/scripts/build-debs.sh` is the local helper that copies `safe/` into a writable build directory and runs `dpkg-buildpackage`; and `.github/workflows/build-debs.yml` builds Debian artifacts in an `ubuntu:24.04` container and publishes the resulting `.deb` files.

3. **Remaining unsafe FFI beyond the original ABI/API boundary.**

- `safe/crates/libcjson/src/hooks.rs:8-11` imports `malloc`, `free`, and `realloc` from the system C library (`libc.so.6`). They exist so the port can honor upstream `cJSON_InitHooks`, allocate C-owned nodes and strings, and expose `cJSON_malloc`/`cJSON_free`. Replacing them with safe Rust would require changing the ownership contract so callers no longer hand raw `cJSON` allocations across the C ABI, or introducing a different allocator abstraction that is not the original cJSON hook API.
- `safe/crates/libcjson/src/number.rs:14-16,26-27` imports `snprintf`, `strtod`, and optionally `localeconv` from `libc.so.6`. They exist to preserve upstream numeric formatting, parsing, and locale-toggled decimal-point behavior. A safe-Rust replacement would need a float parser and formatter that exactly matches cJSON's accepted syntax, 15-digit/17-digit round-trip behavior, and the `ENABLE_LOCALES`/`CJSON_ENABLE_LOCALES` switch.
- `safe/crates/libcjson_utils/src/lib.rs:40-60` imports core `cJSON_CreateArray`, `cJSON_CreateNull`, `cJSON_CreateObject`, `cJSON_CreateString`, `cJSON_GetObjectItem`, `cJSON_GetObjectItemCaseSensitive`, `cJSON_AddItemToArray`, `cJSON_AddItemToObject`, `cJSON_DetachItemFromObject`, `cJSON_DetachItemFromObjectCaseSensitive`, `cJSON_DeleteItemFromObject`, `cJSON_DeleteItemFromObjectCaseSensitive`, `cJSON_Duplicate`, `cJSON_Delete`, `cJSON_malloc`, and `cJSON_free` symbols from the sibling core library. This is internal cross-crate ABI coupling inside the Rust port, not a third-party dependency, but it is still a C ABI boundary that would disappear only if the utils implementation shared a Rust internal API with the core crate instead of reimporting exported C symbols.
- `safe/CMakeLists.txt:174-182,191-212` asks the linker for `${CMAKE_DL_LIBS}`, `-lm`, `-lpthread`, `-lrt`, and `-lutil` when converting the Rust static archives into shared libraries, and it explicitly links `libcjson_utils.so` against `-lcjson`. On the built artifacts from the temporary CMake build directory used for this refresh, `readelf -d` showed that none of `${CMAKE_DL_LIBS}`, `libm`, `libpthread`, `librt`, or `libutil` survive into `DT_NEEDED`. The actual runtime set is:
  - `libcjson.so.1`: `libgcc_s.so.1`, `libc.so.6`, and `ld-linux-x86-64.so.2`.
  - `libcjson_utils.so.1`: `libcjson.so.1`, `libgcc_s.so.1`, `libc.so.6`, and `ld-linux-x86-64.so.2`.
  The remaining non-port libraries therefore come from the compiler/runtime and the system C library, not from extra third-party libraries used by the Rust code itself. Replacing those would require a different toolchain or static-runtime strategy rather than a local source rewrite.
- No syscalls, plugin systems, dynamic module loading (`dlopen`/`dlsym`), or third-party C/C++ dependencies show up in the port sources beyond the libc calls and the internal utils-to-core ABI boundary above.
